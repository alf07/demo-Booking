# Бронирование переговорных

API для создания и отмены бронирований переговорных комнат.

**Стек:** PHP 8.4, Laravel 13, PostgreSQL.

## Запуск проекта

Нужны Docker и Docker Compose.

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
```

После запуска API доступно по адресу `http://localhost:8000/api`.

`migrate:fresh` пересоздаёт таблицы и удаляет существующие данные в базе. Используйте эту команду для локальной установки или тестового окружения.

## Тесты

```sh
docker compose exec app php artisan test
```

Тесты запускаются на PostgreSQL в отдельной базе `testing`.

## API

Все маршруты требуют аутентификацию через Laravel Sanctum. Для JSON-запросов передавайте заголовки:

```http
Accept: application/json
Authorization: Bearer <token>
```

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/api/bookings` | Список бронирований текущего пользователя |
| `POST` | `/api/bookings` | Создание бронирования |
| `DELETE` | `/api/bookings/{id}` | Отмена собственного бронирования |
| `GET` | `/api/rooms/{room}/bookings/today` | Бронирования комнаты на сегодня |

### Создание бронирования

Пример запроса:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-12-02T10:00:00+03:00", "ends_at": "2026-12-02T11:00:00+03:00"}'
```

`user_id` передавать не нужно: автор бронирования определяется на сервере по текущему пользователю.

### Ответы API

- `201 Created` — бронирование создано.
- `204 No Content` — бронирование отменено.
- `401 Unauthorized` — пользователь не аутентифицирован.
- `404 Not Found` — бронирование не найдено среди бронирований текущего пользователя.
- `422 Unprocessable Entity` — ошибка входных данных или бизнес-правил, в том числе занятое время.

## Правила бронирования

- Бронирования одной комнаты не должны пересекаться.
- Встречи, которые идут вплотную друг за другом, разрешены: например, `10:00–11:00` и `11:00–12:00`.
- Продолжительность встречи — от 15 минут до 4 часов включительно.
- Начало и окончание должны попадать на 15-минутную сетку.
- Встреча целиком должна проходить в интервале с 09:00 до 20:00 по местному времени офиса, которому принадлежит комната.
- Даты передаются в ISO 8601 с часовым смещением. Прошедшие даты не запрещены.
- Отменить бронирование может только его автор.

## Как устроена реализация

- `app/Http/Requests/StoreBookingRequest.php` — проверка входных полей и формата дат.
- `app/Http/Controllers/BookingController.php` — обработка HTTP-запросов и формирование ответов.
- `app/Services/BookingService.php` — правила бронирования, проверка пересечений, транзакция, блокировка комнаты, создание и отмена бронирования.
- `tests/Feature/BookingStoreTest.php` — feature-тесты создания бронирований.
- `tests/Feature/BookingDestroyTest.php` — feature-тесты отмены бронирований.

Для работы с моделями используется Eloquent. Отдельный Repository для этой задачи не добавлялся.

Методы `index()` и `today()` в контроллере оставлены без изменений, поскольку доработка этих методов не входила в часть задания, посвящённую реализации.

## Часовые пояса и хранение дат

Клиент передаёт дату со смещением, например `2026-12-02T10:00:00+03:00`. Приложение разбирает значение как конкретный момент времени.

Для проверки рабочего времени начало и окончание переводятся в часовой пояс офиса (`offices.timezone`). После проверок оба значения переводятся в UTC.

В PostgreSQL поля `starts_at` и `ends_at` имеют тип `timestamp without time zone`: сам тип не хранит часовой пояс. Поэтому приложение использует единое соглашение — значения в этих полях записываются и интерпретируются как UTC. Это соглашение должно соблюдаться всеми частями приложения и при работе с уже существующими данными.

## Защита от одновременного бронирования

Создание бронирования выполняется внутри транзакции. Перед проверкой пересечений сервис получает строку комнаты с `lockForUpdate()`.

Запросы на создание брони одной комнаты должны брать блокировку одной и той же строки. Поэтому второй запрос ожидает завершения первой транзакции, а затем проверяет доступность уже с учётом созданной брони.

Эта защита работает, если все операции создания бронирований используют тот же механизм блокировки. Прямая запись в таблицу `bookings` в обход сервиса этой блокировкой не защищена. Для более строгой гарантии на уровне PostgreSQL можно дополнительно использовать ограничение `EXCLUDE` по комнате и диапазону времени.

Отдельный интеграционный тест с двумя параллельными соединениями в текущем наборе тестов не реализован.
