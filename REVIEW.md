# Code Review — demo-booking

Проверенный проект: `rcsi-science/demo-booking`, ветка `master`.

Основные файлы, рассмотренные при ревью:

- `app/Http/Controllers/BookingController.php`
- `routes/api.php`
- `app/Models/Booking.php`, `Room.php`, `Office.php`, `User.php`
- `database/migrations/*create_offices_table.php`
- `database/migrations/*create_rooms_table.php`

- `config/app.php`, `config/database.php`, `config/logging.php`

## Краткий итог

В первую очередь требуется исправить создание и отмену бронирований: сейчас возможны SQL Injection, некорректная проверка временных интервалов, подмена автора бронирования и отмена чужой брони. Отдельно обнаружена проблема хранения времени: PostgreSQL-столбцы объявлены как `timestamp without time zone`, а входные даты с часовым смещением сохраняются без предварительной нормализации к UTC. Из-за этого одинаковый момент времени, присланный с разными смещениями, может оказаться в базе как разное локальное время.

Также `store()` перегружен ответственностями: в одном методе смешаны получение HTTP-входных данных, запрос к БД, проверка бизнес-правил, создание модели, логирование и формирование ответа. Это архитектурное замечание следует учитывать при реализации второй части, но не превращать тестовое в масштабный рефакторинг.

Методы `index()` и `today()` по условию задания изменять не требуется. Их замечания приведены ниже только для ревью.

## 1. `BookingController::store()` — проверка пересечения бронирований

**Файл:** `app/Http/Controllers/BookingController.php`, строки 23–30.

Текущий код:

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");

if ($conflict) {
    return response()->json(['error' => 'Комната занята'], 409);
}
```

### 1.1. SQL Injection — major

Значения `room_id`, `starts_at` и `ends_at`, полученные от клиента, непосредственно вставляются в текст SQL-запроса. Клиент может передать специально сформированное значение, которое изменит условия запроса.

Проблема не в самом `DB::select()`: этот метод поддерживает параметризованные запросы. Уязвимость возникает из-за интерполяции пользовательских данных в SQL-строку.

**Как исправить:** использовать Eloquent или Query Builder с параметрами. В данном случае запрос удобнее выразить через `Booking::query()` и `exists()`: нужны только сведения о наличии конфликта, сами записи загружать не требуется.

### 1.2. Неправильная проверка пересечения интервалов — major

В текущем запросе используются включительные операторы `<=` и `>=`. Поэтому соприкасающиеся интервалы ошибочно считаются пересекающимися.

Пример:

- существующая бронь: 10:00–11:00;
- новая бронь: 11:00–12:00.

По требованиям такие бронирования разрешены. Для интервалов, где момент окончания не входит в интервал, пересечение определяется условиями:

```text
existing.starts_at < new.ends_at
AND existing.ends_at > new.starts_at
```

**Как исправить:** использовать строгие сравнения `<` и `>` после проверки корректности нового интервала.

### 1.3. Низкоуровневый запрос не соответствует простой задаче — minor (замечание по реализации)

Запрос вручную выбирает `id`, хотя вызывающему коду требуется только понять, существует ли хотя бы одна конфликтующая запись. Это можно выразить через Eloquent `exists()`.

**Как исправить:** использовать запрос через модель `Booking` либо Query Builder. Само по себе применение `DB::select()` не является уязвимостью; важно не переносить текущую интерполяцию SQL из контроллера в сервис без изменения способа построения запроса.

## 2. `BookingController::store()` — валидация и временные ограничения

**Файл:** `app/Http/Controllers/BookingController.php`, строки 21–37.

В методе отсутствует полноценная проверка входных данных. До выполнения SQL-запроса приложение не проверяет, что обязательные поля переданы, комната существует, даты имеют требуемый формат и интервал корректен.

### 2.1. Отсутствует валидация входных данных — major

Сейчас данные запроса сразу используются в SQL и Carbon. В частности, не проверяются:

- наличие `room_id`, `title`, `starts_at` и `ends_at`;
- существование комнаты;
- формат дат и наличие смещения часового пояса в ISO 8601;
- что окончание позже начала;
- допустимая продолжительность — от 15 минут до 4 часов;
- соответствие временных границ шагу 15 минут.

Не следует добавлять запрет на бронирование прошедших дат: в задании прямо сказано, что других ограничений на даты нет.

При некорректных данных вместо понятной ошибки валидации клиент может получить SQL-ошибку, исключение при разборе даты или ошибку внешнего ключа.

**Как исправить:** вынести проверку входных данных в Form Request. Проверки бизнес-правил, зависящие от комнаты и её офиса, выполнять после получения валидированной комнаты и дат. Ошибки валидации должны возвращаться в предусмотренном заданием формате 422.

### 2.2. Проверяется только час начала встречи — major

Текущая проверка:

```php
$start = Carbon::parse($request->starts_at);

if ($start->hour < 9 || $start->hour >= 20) {
    return response()->json(['error' => 'Нерабочее время'], 422);
}
```

Проверяется только час начала. Между тем по заданию весь интервал должен находиться в пределах 09:00–20:00.

Например, бронь 19:00–21:00 пройдёт текущую проверку, хотя заканчивается после закрытия офиса. Проверка начала до 09:00 в коде есть, но она также выполняется по часу из клиентского часового смещения, а не по местному времени офиса.

**Как исправить:** проверять обе границы интервала после преобразования в местный часовой пояс офиса: начало не раньше 09:00, окончание не позже 20:00.

### 2.3. Не учитывается часовой пояс офиса — major

В `config/app.php` часовой пояс приложения установлен в UTC. В `store()` вызывается `Carbon::parse()` для даты, присланной клиентом, а затем проверяется свойство `hour` полученного объекта.

Входное значение ISO 8601 может содержать любое смещение. Час, полученный непосредственно из такого значения, не обязательно является местным часом офиса. Одна и та же точка времени может быть представлена, например, как `10:00+03:00` и `07:00Z`.

**Как исправить:** получить офис выбранной комнаты, взять его `timezone` и преобразовать оба момента времени в этот часовой пояс перед проверкой рабочего графика.

### 2.4. Временные значения не нормализуются перед сохранением — major

**Файлы:**

- `database/migrations/2026_10_29_000003_create_bookings_table.php`;
- `app/Models/Booking.php`;
- `app/Http/Controllers/BookingController.php`.

В миграции используются:

```php
$table->timestamp('starts_at');
$table->timestamp('ends_at');
```

Для PostgreSQL Laravel создаёт тип `timestamp without time zone`. В модели для этих полей настроен cast `datetime`, но cast сам по себе не задаёт единую временную зону хранения.

Сейчас `Carbon::parse()` разбирает ISO 8601 с часовым смещением в соответствующем часовом поясе, а Eloquent при записи форматирует дату для столбца `timestamp without time zone` без сохранения смещения. Поэтому два представления одного момента времени, например `10:00+03:00` и `07:00Z`, могут сохраниться как разные значения `10:00` и `07:00`.

Это влияет не только на отображение, но и на проверку пересечений: одинаковый реальный момент, присланный с разными смещениями, может сравниваться как разное время.

**Как исправить:** определить единый контракт хранения и привести входные даты к UTC до записи. При проверке рабочих часов переводить их в часовой пояс офиса, а для ответа клиенту — в нужный часовой пояс. Альтернативно можно использовать PostgreSQL `timestamptz`, но переход на этот тип также требует согласованной нормализации и проверки поведения приложения; простая смена типа столбца сама по себе не заменяет корректную обработку часовых поясов.

## 3. `BookingController::store()` — создание бронирования

**Файл:** `app/Http/Controllers/BookingController.php`, строка 37.

Текущий код:

```php
$booking = Booking::create($request->all());
```

### Возможность подмены автора бронирования — major

`$request->all()` передаёт в массовое заполнение все входные данные клиента. В модели `Booking` атрибут `user_id` включён в список разрешённых для массового заполнения:

```php
#[Fillable(['room_id', 'user_id', 'starts_at', 'ends_at', 'title'])]
```

Следовательно, авторизованный пользователь может передать чужой `user_id` и создать бронирование от имени другого пользователя.

Middleware `auth:sanctum` устанавливает личность пользователя, отправившего запрос, но текущий код не использует эту информацию для назначения автора.

**Как исправить:** передавать в создание только валидированные поля и создавать бронь через связь текущего пользователя, например `$request->user()->bookings()->create(...)`. `user_id` должен определяться сервером, а не приниматься от клиента.

## 4. `BookingController::store()` — контекст логирования

**Файл:** `app/Http/Controllers/BookingController.php`, строки 39–40.

Текущий код:

```php
Log::withContext(['booking_id' => $booking->id]);
Log::channel('bookings')->info('Booking created');
```

### Контекст добавляется не в тот логгер — minor

Вызов `Log::withContext()` через фасад без выбора канала применяется к логгеру по умолчанию. Следующая строка явно выбирает отдельный канал `bookings`.

В конфигурации `config/logging.php` канал `bookings` записывает сообщения в `storage/logs/bookings.log`, а в `.env.example` каналом по умолчанию указан `stack`. Контекст, добавленный к логгеру по умолчанию, не гарантированно попадёт в отдельный логгер `bookings`.

**Как исправить:** передавать контекст непосредственно в запись нужного канала:

```php
Log::channel('bookings')->info('Booking created', [
    'booking_id' => $booking->id,
]);
```

## 5. `BookingController::destroy()` — отмена бронирования

**Файл:** `app/Http/Controllers/BookingController.php`, строки 45–50.

Текущий код:

```php
public function destroy($id)
{
    Booking::findOrFail($id)->delete();

    return response()->noContent();
}
```

### Не проверяется владелец бронирования — major

Маршрут защищён middleware `auth:sanctum`, но метод ищет бронирование только по ID и сразу удаляет его. Любой авторизованный пользователь, знающий ID чужой брони, может отменить её.

Это проблема авторизации на уровне объекта (IDOR): факт аутентификации не означает, что пользователь имеет право удалять любую запись.

**Как исправить:** искать бронирование через связь текущего пользователя (`$request->user()->bookings()->findOrFail($id)`) либо использовать Laravel Policy. Первый вариант вернёт 404 для бронирования, которое не принадлежит текущему пользователю; Policy может вернуть 403. Оба подхода позволяют запретить отмену чужой брони.

## 6. `BookingController::today()` — получение бронирований на сегодня

**Файл:** `app/Http/Controllers/BookingController.php`, строки 52–60.

Текущий код:

```php
public function today(Room $room)
{
    return $room->bookings()
        ->whereDate('starts_at', today())
        ->get()
        ->map(fn ($b) => [
            'time' => $b->starts_at . ' – ' . $b->ends_at,
            'author' => $b->user->name,
        ]);
}
```

По условию задания метод `today()` исправлять не требуется, но его проблемы следует отметить в ревью.

### 6.1. Используется дата приложения, а не локальная дата офиса — major

В `config/app.php` задан UTC, а `today()` использует часовой пояс приложения. В результате около полуночи локальная дата Москвы или Новосибирска может отличаться от даты UTC, и метод может выбрать бронирования не за тот календарный день, который является сегодняшним для офиса.

Корректный подход при хранении временных значений в UTC — определить начало и начало следующего дня в часовом поясе офиса, перевести обе границы в UTC и выбирать записи по диапазону `starts_at >= startUtc` и `starts_at < nextDayUtc`.

### 6.2. Нет явного перевода времени в часовой пояс офиса — minor

Поля `starts_at` и `ends_at` преобразуются в строки напрямую. Явного преобразования в часовой пояс офиса и явного формата отображения нет.

**Как исправить:** перед формированием ответа преобразовывать даты в часовой пояс офиса и задавать согласованный формат.

### 6.3. N+1 при получении авторов бронирований — minor

При обращении к `$b->user->name` Eloquent лениво загружает пользователя для каждой брони. Для списка из N бронирований это может привести к одному запросу для бронирований и дополнительным запросам для связанных пользователей.

**Как исправить:** заранее загружать связь, например `with('user:id,name')`.

### Замечание, которое не следует считать подтверждённым дефектом

Любой авторизованный пользователь может запросить расписание любой комнаты и увидеть имена авторов. Это может быть вопросом конфиденциальности, но в предоставленных требованиях нет ограничения на просмотр расписания или имён авторов. Без такого бизнес-правила нельзя утверждать, что текущий доступ ошибочен.

## 7. `BookingController::index()` — список своих бронирований

**Файл:** `app/Http/Controllers/BookingController.php`, строки 14–19.

Текущий код:

```php
public function index(Request $request)
{
    return Booking::where('user_id', $request->user()->id)
        ->orderByRaw('starts_at DESC')
        ->paginate(20);
}
```

Существенных функциональных или security-проблем в этом методе не обнаружено:

- выборка ограничена текущим пользователем;
- применяется пагинация;
- сортировка выполняется по дате начала.

`orderByRaw('starts_at DESC')` выглядит подозрительно, поскольку используется raw-метод, но строка статическая и не содержит пользовательского ввода. SQL Injection здесь нет. Для читаемости можно использовать `orderByDesc('starts_at')`, но это необязательное улучшение, а не исправление уязвимости.

## 8. Архитектурное замечание: слишком много ответственности в `store()`

**Файл:** `app/Http/Controllers/BookingController.php`, метод `store()`.

Метод одновременно выполняет несколько разных задач:

- получает и читает входные данные HTTP-запроса;
- строит запрос к БД и проверяет наличие пересечения;
- разбирает даты и проверяет временные ограничения;
- создаёт запись бронирования;
- записывает событие в лог;
- выбирает HTTP-статусы и формирует ответы.

В результате контроллер не только связывает HTTP-запрос с приложением, но и содержит значительную часть сценария создания бронирования. Это усложняет поддержку метода: изменения бизнес-правил затрагивают HTTP-код, а отдельные части сценария сложнее тестировать и повторно использовать.

**Рекомендация по разделению ответственности:**

1. `StoreBookingRequest` — проверка формы входных данных: обязательные поля, типы, формат ISO 8601 со смещением, базовые ограничения. Не нужно помещать сюда всю бизнес-логику только ради того, чтобы Form Request стал большим.
2. Небольшой `CreateBooking` Action (либо существующий в проекте прикладной сервис, если он появится) — координация сценария создания: получить нужную комнату и офис, применить правила времени, проверить пересечение, создать бронь и записать событие.
3. `BookingController` — получить валидированные данные и текущего пользователя, вызвать Action, преобразовать успешный результат или ожидаемую бизнес-ошибку в HTTP-ответ.

**Важное уточнение по работе с БД:** не следует просто перенести текущий `DB::select()` из контроллера в сервис. Это переместит код, но не улучшит решение. Здесь нужен не произвольный raw SQL, а понятный запрос через `Booking::query()` / Query Builder с параметризованными значениями и `exists()`, поскольку требуется только проверить наличие конфликтующей записи. Сам по себе `DB::select()` не является ошибкой и может быть уместен для сложного или специфичного SQL, но для этой простой проверки он неоправданно усложняет код.

Отдельный Repository ради одного запроса также не требуется. Достаточно Action, который координирует сценарий, и Eloquent для чтения/создания моделей. Логирование можно оставить в Action рядом с успешным созданием либо вынести в отдельный механизм только при появлении более сложных требований к событиям.

Это архитектурное замечание уровня **minor**: оно не заменяет исправление функциональных дефектов и само по себе не требует масштабного рефакторинга. При выполнении второй части достаточно разделить обязанности в той мере, которая делает `store()` понятным и тестируемым.

## 9. Конкурентное создание бронирований — бонус задания

В `store()` сначала выполняется проверка занятости комнаты, а затем отдельной операцией создаётся бронь. Эти действия не защищены общей транзакцией и блокировкой.

При двух одновременных запросах возможно следующее:

1. Первый запрос проверяет слот и не находит конфликт.
2. Второй запрос проверяет тот же слот и также не находит конфликт.
3. Оба запроса создают бронирования.

В результате появляются пересекающиеся брони.

**Вариант исправления:** выполнять проверку и создание в транзакции, предварительно блокируя строку соответствующей комнаты через `lockForUpdate()`. Все операции создания бронирования для одной комнаты должны следовать этому же правилу блокировки.

Более сильный вариант для PostgreSQL — ограничение `EXCLUDE` по комнате и временному диапазону (с использованием подходящего range-типа и GiST/`btree_gist`).

По условию задания допускается не реализовывать защиту от гонки, а описать выбранный подход в README.

## 10. Примечания: что выглядит подозрительно, но не является подтверждённой ошибкой

1. `orderByRaw('starts_at DESC')` в `index()` — безопасно в текущем виде, поскольку выражение статическое. `orderByDesc()` будет просто выразительнее.
2. HTTP 409 при занятом слоте — сам по себе не является ошибкой. Это осмысленный статус конфликта состояния. Требование 422 относится к ошибкам валидации; не следует автоматически заменять 409 на 422, если контракт API отдельно не требует 422 именно для конфликта бронирования.
3. Возможность просматривать расписание других комнат и имена авторов в `today()` нельзя объявить дефектом без требования о разграничении такого доступа.
4. В `config/app.php` часовой пояс UTC сам по себе является нормальным выбором. Ошибка заключается в отсутствии согласованного преобразования входных и выходных дат и местного времени офиса.

## 11. Область необходимых изменений

По заданию необходимо доработать `store()` и `destroy()`, добавить Feature-тесты и описать бонусное решение. Поэтому рекомендуется:

- исправить проверку пересечений и защитить запрос от SQL Injection;
- реализовать валидацию входных данных и все ограничения временного интервала;
- нормализовать входящие моменты времени к UTC до сохранения;
- назначать автора только по текущему авторизованному пользователю;
- запретить удаление бронирований, принадлежащих другим пользователям;
- исправить передачу контекста в канал логирования;
- добавить Feature-тесты на все правила из задания.

Методы `index()` и `today()` оставить без изменений, как прямо указано в задании; замечания по ним оставить в этом документе. Архитектурный рефакторинг выполнять только в объёме, который помогает корректно реализовать `store()` и не создаёт лишних абстракций.

**Ограничение проверки:** это статическое ревью исходников. Автоматические тесты, Docker-контейнеры и фактические HTTP-ответы в рамках этой проверки не запускались.
